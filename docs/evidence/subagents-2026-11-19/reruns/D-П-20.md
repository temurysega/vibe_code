# П-20 · Заявки и справки: от формы до документа

## Промпт (дословно из методички)

```text
Заявки — раздел REQ, самый важный сквозной сценарий для жюри. Студент проходит путь от выбора
справки до готового документа и всё время понимает, что происходит.

Каталог (server/domain/requests.js; список полей общий для браузера и сервера):
- справки: об обучении (электронная или бумажная, ru/en), для посольства (en), для военкомата
  (только бумажная), выписка оценок, о стипендии;
- заявления: пропуск по уважительной причине, материальная помощь (только для бюджетников),
  индивидуальный график сессии, программа обмена (решает отдел мобильности), запись на пересдачу
  (только при долге: выбор дисциплины и удобной даты);
- у каждого вида: описание, срок, способы получения, поля с типами и ограничениями.

Форма:
- ФИО, факультет, курс и группа подставляются из профиля — студент заполняет только недостающее;
- сервер проверяет обязательность, длину, допустимые варианты и даты строго по календарю
  (31 февраля — ошибка, а не 3 марта); дубликат активной заявки того же вида молча не создаётся;
- при ошибке введённые поля сохраняются, рядом с полем — что не так, фокус переходит к первому
  ошибочному полю.

Статусы: Подана → В работе → Готова → Выдана, или Одобрена / Отклонена; Отменена — пока обработка
не началась. Переходы только вперёд и только допустимые для вида. Каждое изменение пишется в
request_events (кто, когда, комментарий) и создаёт уведомление со ссылкой на заявку.

Карточка заявки — как отслеживание посылки: номер, текущий статус, история. Для бумажной —
где и когда забрать. Для электронной — «Открыть и скачать»: демонстрационный документ с кодом и
ссылкой проверки (/api/verify/:code открывается без входа и показывает только номер, дату и
инициалы), сохранение в PDF через печать браузера и надпись «Вымышленный образец без электронной
подписи». Не рисуй декоративный узор, похожий на QR-код: если QR нет, его не должно быть и на
картинке.

Справка о стипендии: таблица шести завершённых месяцев с суммами и итогом, месяцы без выплаты
обозначены отдельно; снимок данных фиксируется в момент подачи. Все суммы демонстрационные — так
и написано в документе.

Демо-автоматика: без участия сотрудника заявка примерно через минуту переходит «в работу»,
а электронная справка становится готовой примерно через 8 минут (DEMO_AUTOPILOT_SCALE=1).
Первое действие сотрудника отключает автоматику. Это нужно, чтобы жюри успело само принять решение
в кабинете деканата.

Безопасность — главное:
- студент берётся только из сессии; чтение, отмена и получение документа ищут заявку условием
  WHERE id = ? AND student_id = ?; чужая → 404 «Заявка не найдена» — тот же ответ, что и для
  несуществующей;
- скрытая кнопка в интерфейсе не заменяет проверку в API.

Тесты: два студента и чужой номер заявки (чтение, отмена, документ); 31 февраля; дубль;
недопустимый переход статуса; сохранение — создать заявку, закрыть сервер, открыть тот же файл базы
и сравнить поля и историю.
```

## Ответ Claude Sonnet 5.5 · 19.11.2026

Перед кодом — короткий план и несколько решений, которые стоит зафиксировать.

**План по файлам**
1. `server/domain/requests.js` — каталог `TYPES` (10 видов: 5 справок, 5 заявлений) с полями `fields` (тип, обязательность, `min`/`max`, `options`); `catalogFor(student)` скрывает материальную помощь не-бюджетникам, помечает пересдачу недоступной без долгов и подставляет дисциплины-долги и три ближайшие даты в будни. Один каталог отдаётся браузеру через `GET /api/requests/types`, сервер валидирует по нему же.
2. Валидация: обязательность, длина, `select` только из списка, даты по календарю. Дата проверяется обратным сравнением: разобрать `YYYY-MM-DD` и убедиться, что `toISOString()` вернул ту же строку (иначе 31 февраля тихо станет 3 марта).
3. Статусы и история: `setStatus` пишет `request_events` и создаёт уведомление со ссылкой `#/requests/:id`. Таблица допустимых переходов — на сервере; «ранг» статуса не даёт автоматике откатить решение сотрудника.
4. Безопасность: каждый маршрут заявки идёт через `requireStudent`, а поиск — `WHERE id = ? AND student_id = ?`; чужая и несуществующая отвечают одинаково `404 «Заявка не найдена»`.
5. Документ: `GET /api/requests/:id/document` только для электронной справки в статусах «Готова/Выдана»; `GET /api/verify/:code` — без входа, код 8 hex, в ответе номер, название, дата и инициалы.
6. Стипендия: снимок шести месяцев считается один раз при подаче и хранится в `payload._stipend`.
7. Автоматика: план шагов в `requests.plan`, интервал масштабируется `DEMO_AUTOPILOT_SCALE`; действие сотрудника обнуляет план.

**Два уточнения к постановке**
- «Дубликат молча не создаётся» — я бы не делал это молча: возвращаю `409` с номером существующей заявки, чтобы интерфейс мог открыть её. Сравниваются вид и полезная нагрузка среди «Подана/В работе».
- QR: пока нет реализации кодирования, на документе только текстовый код и ссылка; рисовать псевдо-QR не буду.

**Тесты** (`node:test`, временная база): чужая заявка — чтение, отмена, документ → 404; 31 февраля → 422 с ошибкой поля; повтор → 409; недопустимый переход → 409; закрыть базу, открыть тот же файл, сравнить поля и историю; подмена `student_id` в теле не меняет владельца.

**Что не могу подтвердить сам:** вид документа при печати в PDF и поведение фокуса на ошибке — это браузерные сценарии (Playwright), их нужно запустить отдельно.
