# П-05 · Спецификация с критериями приёмки
## Промпт (дословно из методички)
```text
Теперь превратим концепцию в спецификацию, по которой будут работать все агенты: ты, Codex и
Qwen Code. Поэтому она должна быть однозначной — каждое требование проверяется тестом или
конкретным действием в браузере.

Прочитай docs/ai/PRODUCT.md и docs/ai/REQUIREMENTS.md и создай docs/ai/SPEC.md.

Разделы: AUTH (вход и профиль), SCH (расписание), GRD (успеваемость), REQ (заявки и справки),
DEAN (кабинет деканата), NTF (уведомления), AST (помощник), PLAY (игровой слой),
UX (общие правила интерфейса и 360 px), SEC (безопасность).

Для каждого раздела:
- 2–4 пользовательские истории;
- какие данные нужны и откуда они берутся;
- состояния: загрузка, пусто, ошибка с повтором, успех;
- критерии приёмки с номерами (SCH-01, SCH-02…) в форме «Дано / Когда / Тогда»;
- связи с другими разделами (например, NTF-04: решение деканата по заявке → уведомление со ссылкой
  именно на эту заявку).

Обязательно включи:
- REQ: студент открывает чужую заявку по адресу → сервер отвечает 404 «Заявка не найдена»;
- REQ: невозможная дата (31 февраля) отклоняется, а не превращается в 3 марта;
- AUTH: после выхода и входа другим студентом в форме — данные нового студента;
- UX: на 360 px нет горизонтальной прокрутки страницы; у кнопок-иконок есть доступные названия;
  диалоги удерживают фокус и закрываются по Escape.

В конце — таблица демо-аккаунтов (логин, кто это, что показывает) и черновой маршрут для жюри:
Алина отправляет справку → деканат принимает решение → Алина получает уведомление и документ →
Тимур по той же ссылке видит «Заявка не найдена».

Не придумывай функций, которых нет в PRODUCT.md. Если для критерия не хватает решения — запиши
вопрос в конец документа.
```
## Ответ Claude Sonnet 5.5 · 19.11.2026
Черновик `docs/ai/SPEC.md`. Номера стабильны, чтобы тест можно было сослаться на критерий.

**Разделы:** AUTH, SCH, GRD, REQ, DEAN, NTF, AST, PLAY, UX, SEC. Для каждого: 2–4 истории, источник данных (сид или ввод пользователя, всё вымышленное), состояния «загрузка / пусто / ошибка с повтором / успех», критерии, связи.

**AUTH** (истории: войти; увидеть профиль; сменить пароль; выйти)
- AUTH-01. Дано: верный логин и пароль. Когда: вход. Тогда: cookie `HttpOnly`, ответ содержит CSRF-токен.
- AUTH-02. Дано: пять неверных паролей. Когда: шестая попытка. Тогда: 429 и `Retry-After`.
- AUTH-03. Дано: вошёл студент А, выход, вход студента Б. Когда: открыта форма заявки. Тогда: поля содержат данные Б, чат пуст.

**SCH**
- SCH-01. Дано: пара перенесена деканатом. Когда: студент группы открывает неделю. Тогда: пара помечена, видны новая аудитория и этаж.
- SCH-02. Дано: запрос недели `2025-W53`. Тогда: 400.

**GRD**
- GRD-02. Дано: дисциплина ниже порога. Тогда: зона риска и «сколько баллов не хватает до следующей оценки».
- GRD-03. Пустой список: сообщение «оценок пока нет», не пустой экран.

**REQ**
- REQ-01. Дано: заявка Алины. Когда: Тимур открывает её адрес. Тогда: 404 «Заявка не найдена» (не 403).
- REQ-02. Дано: дата 31 февраля. Когда: отправка. Тогда: 422 с ошибкой поля, 3 марта не подставляется.
- REQ-03. Дано: `student_id` в теле запроса. Тогда: владелец определяется только по сессии.
- REQ-05. Дано: статус «готово». Тогда: документ с кодом проверки и пометкой «образец».

**DEAN**
- DEAN-01. Сотрудник МО видит только заявки групп МО; заявка другого факультета даёт 404.
- DEAN-02. Отказ без причины (меньше 10 символов) отклоняется.
- DEAN-03. 11-е объявление за 10 минут: 429.

**NTF**
- NTF-01. Дано: деканат закончил заявку. Тогда: уведомление студенту со ссылкой именно на эту заявку.
- NTF-02. Дедлайн через 3 дня создаёт одно напоминание.

**AST**
- AST-01. Без ключа ИИ ответ строится по правилам и содержит пометку источника.
- AST-03. В запрос уходят данные только текущего студента.

**PLAY**
- PLAY-01. Закрытую вещь нельзя надеть запросом к API.
- PLAY-02. Счёт забега ограничивается реальным временем; лимит 5 минут в день.
- PLAY-03. Учебные задачи доступны без игры.

**UX**
- UX-01. На 360 px `scrollWidth <= innerWidth`.
- UX-02. У кнопок-иконок есть `aria-label`.
- UX-03. Диалог закрывается по Escape, фокус возвращается на открывавшую кнопку.

**SEC.** Ключи только из окружения; CSP без внешних адресов; пароль в базе только хешем.

**Демо-аккаунты:** `a.morozova` (риск, переносы), `t.aliev` (первокурсник, чужая ссылка), `k.lebedeva` (долг), `dekanat.mo`.

**Маршрут жюри:** Алина отправляет справку → деканат принимает решение → Алина видит уведомление и документ → Тимур по той же ссылке видит «Заявка не найдена».

## Сверка с репозиторием
- `docs/ai/SPEC.md` в репозитории нет, нумерации SCH-01…SEC-xx тоже нет. Роль спецификации частично выполняют `docs/JURY_GUIDE.md`, `docs/CONTEST_AUDIT.md` и тесты.
- Реализованы: 404 чужой заявки (`test/security.test.js`, «студент не открывает чужую заявку…»); невозможные даты, 422 и 400 для `2025-W53` (`test/backend-regressions.test.js`); `student_id` в теле игнорируется (там же); лимит 10 объявлений (`test/dean-limits.test.js`); смена аккаунта (`test/browser-flows.py`, `test/browser-session-sync.py`).
- UX: проверки 360 px, подписей полей и Escape с возвратом фокуса — `test/browser-accessibility.py`, `test/browser-first-actions.py`.
- Маршрут жюри стал `docs/JURY_GUIDE.md`, пройден `test/browser-flows.py`.
- Отличие: описано «автопилот заявок» (`docs/ARCHITECTURE.md`, ~8 минут), в моём черновике вопрос про него был открыт.
