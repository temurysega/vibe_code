## П-05 · Спецификация с критериями приёмки

> - **Кому:** Claude Code
> - **Опирается на:** `docs/ai/PRODUCT.md`, `docs/ai/REQUIREMENTS.md`
> - **Даёт:** `docs/ai/SPEC.md` с пронумерованными критериями (SCH-01, REQ-07…)
> - **Приёмы:** «Дано / Когда / Тогда» · номера для трассировки от требования до теста · вопросы вместо выдумок

```text
Теперь превратим концепцию в спецификацию, по которой будут работать все агенты: ты, Codex и
Qwen Code. Поэтому она должна быть однозначной — каждое требование проверяется тестом или
конкретным действием в браузере.

Прочитай docs/ai/PRODUCT.md и docs/ai/REQUIREMENTS.md и создай docs/ai/SPEC.md.

Разделы: AUTH (вход и профиль), SCH (расписание), GRD (успеваемость), REQ (заявки и справки),
DEAN (кабинет деканата), NTF (уведомления), AST (помощник), PLAY (игровой слой),
UX (общие правила интерфейса и 360 px), SEC (безопасность).

Для каждого раздела:
- 2–4 пользовательские истории;
- какие данные нужны и откуда они берутся;
- состояния: загрузка, пусто, ошибка с повтором, успех;
- критерии приёмки с номерами (SCH-01, SCH-02…) в форме «Дано / Когда / Тогда»;
- связи с другими разделами (например, NTF-04: решение деканата по заявке → уведомление со ссылкой
  именно на эту заявку).

Обязательно включи:
- REQ: студент открывает чужую заявку по адресу → сервер отвечает 404 «Заявка не найдена»;
- REQ: невозможная дата (31 февраля) отклоняется, а не превращается в 3 марта;
- AUTH: после выхода и входа другим студентом в форме — данные нового студента;
- UX: на 360 px нет горизонтальной прокрутки страницы; у кнопок-иконок есть доступные названия;
  диалоги удерживают фокус и закрываются по Escape.

В конце — таблица демо-аккаунтов (логин, кто это, что показывает) и черновой маршрут для жюри:
Алина отправляет справку → деканат принимает решение → Алина получает уведомление и документ →
Тимур по той же ссылке видит «Заявка не найдена».

Не придумывай функций, которых нет в PRODUCT.md. Если для критерия не хватает решения — запиши
вопрос в конец документа.
```

**Если ИИ ошибся**
- Критерии вида «интерфейс удобный»: «Каждый критерий должен описывать наблюдаемое поведение.
  Перепиши UX-03, UX-05 и GRD-07 так, чтобы их можно было проверить скриптом или конкретным
  действием».

**В репозитории:** есть `docs/JURY_GUIDE.md` (маршрут жюри) и сквозной тест `test/browser-flows.py`. Файла
`docs/ai/SPEC.md` в проекте не было, поэтому «из SPEC» они не выросли; методичка предлагает порядок «сначала
SPEC, потом маршрут и тест».

## П-06 · Выбор стека: решение с обоснованием

> - **Кому:** Claude Code
> - **Даёт:** `docs/ai/DECISIONS.md` (ADR-001…ADR-005)
> - **Приёмы:** сравнение по явным критериям · просьба оспорить наш выбор · честный раздел о масштабировании

```text
Выберем стек. Условия: прототип делает один человек с ИИ-ассистентами за несколько дней; его нужно
опубликовать на небольшом VPS и держать до 28 ноября; жюри будет открывать его с телефона;
безопасность проверяют всерьёз; кода должно быть столько, чтобы его могли прочитать и агенты,
и эксперты.

Сравни три варианта в таблице:
A) Next.js + PostgreSQL + ORM;
B) Python (FastAPI) + SPA на React;
C) Node.js без фреймворков (встроенные node:http, node:sqlite, node:crypto, node:test) +
   фронтенд на ES-модулях без сборки.

Критерии: число зависимостей и риск цепочки поставок; простота публикации; насколько легко агенту
и человеку понять весь код; тестирование; скорость на мобильном интернете; путь к масштабированию.

Мой предварительный выбор — C: Node.js не ниже 22.13 (там есть node:sqlite), SQLite-файл на
постоянном томе, hash-роутер и подгрузка экранов через import(). Проверь этот выбор критически:
если видишь серьёзную причину выбрать иначе — скажи прямо.

Оформи в docs/ai/DECISIONS.md записи ADR в формате «Контекст / Решение / Последствия / Когда
пересмотреть»:
- ADR-001 стек;
- ADR-002 SQLite и где хранится файл базы;
- ADR-003 серверные сессии вместо JWT (нужен отзыв сеанса и список активных входов);
- ADR-004 фронтенд без сборки;
- ADR-005 внешний ИИ только с сервера, с резервными правилами.

В разделе о масштабировании честно перечисли, что потребуется при росте: адаптер PostgreSQL,
общее хранилище сессий, лимиты в Redis, один исполнитель фоновых задач, нагрузочные тесты.
Это план, а не готовая возможность, — так и подпиши.
```

**Если ИИ ошибся**
- «Легко масштабируется заменой строки подключения»: «Для node:sqlite это неправда: синхронный API,
  другой диалект SQL, лимиты в памяти процесса. Перечисли конкретные работы и убери обещание».

**В репозитории:** `docs/ARCHITECTURE.md` (таблица «Сейчас → что понадобится при росте»),
`package.json` — единственная зависимость, SDK Anthropic. Готовые ADR — в
[`docs/ai/DECISIONS.md`](../ai/DECISIONS.md).

## П-07 · Модель данных и демо-данные от текущей даты

> - **Кому:** Claude Code в план-режиме
> - **Опирается на:** `SPEC.md`, ADR-002
> - **Даёт:** `server/schema.sql`, план `server/seed/`
> - **Приёмы:** «правила + исключения» для расписания · однострочное обоснование каждой таблицы · сначала схема связей, потом SQL

```text
Спроектируй модель данных в server/schema.sql (SQLite). Прочитай SPEC.md и ADR-002.

Сущности: faculties, groups, students, staff, users, sessions, teachers, disciplines, lessons,
schedule_changes, enrollments, assessments, exams, deadlines, requests, request_events,
notifications, notification_reads, play_state, game_runs, audit_log, meta.

Принципы:
- расписание = регулярные занятия (день недели, номер пары, чётность) + журнал изменений (отмена,
  перенос, смена аудитории, замена преподавателя, дополнительное занятие). Неделю собираем на лету:
  деканат меняет одну запись, а не расписание целиком;
- у заявки есть история (request_events): кто, когда, из какого статуса в какой, комментарий;
- адресат уведомления — весь вуз, факультет, группа или один студент; прочитанность хранится на
  сервере отдельно для каждого студента;
- дедлайн бывает групповым и персональным — персональный не должен попадать другим студентам той же
  группы;
- у студентов только учебные данные: без паспорта, СНИЛС и адреса;
- в sessions хранится не токен, а его SHA-256; в users — хеш пароля.

Над каждой таблицей — комментарий в одну строку: зачем она нужна. Добавь внешние ключи и индексы
под частые запросы «по владельцу» (student_id, group_id).

План демо-данных (server/seed/): данные строятся от текущей даты по Москве, чтобы демо всегда было
«живым» — ближайшие переносы, дедлайн послезавтра, справка, которая скоро станет готовой.
Команда npm run seed пересоздаёт данные — пометь её в README как разрушающую.

Сначала пришли схему связей (текстом или mermaid) и спорные места, потом SQL.
```

**Если ИИ ошибся**
- Хранит расписание готовыми неделями: «Так деканат не сможет отменить одну пару без пересборки
  недель. Верни модель "регулярные занятия + журнал изменений"».
- Хранит токен сессии как есть: «Утечка базы не должна давать вход. Храни SHA-256 токена — сам токен
  знает только браузер».

**В репозитории:** `server/schema.sql` (коммит `832c17b` и по коммиту на каждую таблицу с её
обоснованием в сообщении), `server/seed/`.

## П-08 · Модель угроз → инварианты и тест-план безопасности

> - **Кому:** Claude Code; затем проверка субагентом `security-auditor`
> - **Даёт:** черновик `docs/SECURITY.md`, нумерованные инварианты для `AGENTS.md`, список тестов для `test/security.test.js`
> - **Приёмы:** угрозы именно этого продукта, а не общий чек-лист · связка «атака → инвариант → место → тест» · явные параметры, которые агент может оспорить

```text
Безопасность жюри проверяет руками: подставляет чужой адрес, ищет ключи в коде и браузере, смотрит,
как хранятся пароли. Давай заранее составим модель угроз именно для нашего кабинета, а не общий
список OWASP.

Пройди по угрозам и для каждой дай: сценарий атаки в одну фразу → инвариант (правило, которое код
соблюдает всегда) → где он обеспечивается (файл или слой) → автотест, который это проверяет.

Обязательно разбери:
1. Чужие данные через подстановку id в адресе или теле запроса (заявки, документы, уведомления).
2. Студент вызывает API деканата; сотрудник одного факультета смотрит заявки другого.
3. Подделка изменяющего запроса с чужого сайта (CSRF).
4. Кража и подбор сессии; хранение токенов.
5. Перебор пароля, в том числе параллельными запросами, которые обгоняют счётчик попыток.
6. Внедрение разметки через объявления деканата и комментарии к заявке.
7. Утечка ключей ИИ-провайдера: код, public/, логи, скриншоты, история Git.
8. Помощник получает данные другого студента или выполняет инструкции, спрятанные в данных.
9. Злоупотребление общим демо-стендом: публичный аккаунт деканата рассылает бесконечные объявления;
   кто-то меняет общий демо-пароль.
10. Данные прежнего пользователя в интерфейсе после смены аккаунта: кеши, формы, история чата,
    соседняя вкладка.
11. Выход за пределы public/ при раздаче статики; раскрытие стека в ошибках; внешние ресурсы в CSP.

Параметры, которые я предлагаю: scrypt (N=16384, r=8, p=1, соль 16 байт); токен сессии —
32 случайных байта, в базе SHA-256; cookie HttpOnly и SameSite=Lax, в продакшене Secure и префикс
__Host-; сессия 12 часов, простой 2 часа; 5 неудачных входов на пару «адрес + логин» и 30 на адрес
за 15 минут → 429 с Retry-After; тело JSON не больше 64 КБ. Если считаешь что-то слабым — предложи
замену с обоснованием.

Результат: черновик docs/SECURITY.md простыми словами для жюри, нумерованный список инвариантов
для AGENTS.md и список тестов для test/security.test.js с названиями.
```

**Если ИИ ошибся**
- Роль проверяется только в интерфейсе (кнопка скрыта): «Скрытая кнопка — не защита. Покажи строку
  на сервере, где проверяется, что сотрудник видит только свой факультет».
- Чужая заявка отвечает 403: «403 подтверждает, что такая заявка существует. Нужен 404 с тем же
  текстом, что и для несуществующей».

**В репозитории:** `docs/SECURITY.md`, `server/security/` (`password.js` — `26a17f0`,
`session.js` — `ec13338`, `rateLimit.js` — `a7057e8`), `test/security.test.js` (`ab24051`),
раздел «Инварианты» в `AGENTS.md`.
