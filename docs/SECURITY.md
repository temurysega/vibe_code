# Безопасность

Реализованные меры защиты и их ограничения. Автотесты в `test/security.test.js` проверяют
конкретные сценарии: доступ без входа, разделение студентов и факультетов, CSRF, пароли,
завершение сессии и заголовки. Это не утверждение об отсутствии всех уязвимостей;
актуальный результат запуска фиксируется в `docs/CONTEST_AUDIT.md`.

## Студент видит только свои данные

- Идентификатор студента берётся **только из сессии** (`server/security/auth.js`). Ни один маршрут
  не принимает id студента из адреса или тела запроса: `/api/me`, `/api/grades`, `/api/schedule`
  всегда отдают данные владельца сессии.
- Заявка по id ищется условием `WHERE id = ? AND student_id = ?` (`server/routes/requests.js`).
  Подставленный чужой id даёт **404**, а не 403 — так не раскрывается даже факт существования заявки.
  То же для отмены и электронной справки.
- Уведомления выбираются по адресату (весь вуз, факультет, группа или лично студент); отметить
  прочитанным можно только адресованное этому студенту.
- Деканат работает в границах своего факультета: каждый запрос проверяет `g.faculty_id = staff.faculty_id`.
  Роли разведены: студенту закрыт `/api/dean/*`, сотруднику — студенческие разделы.
- Проверка справки по коду (`/api/verify/:code`) открыта без входа, но раскрывает только номер,
  название, дату и инициалы владельца. Код новых справок — 16 шестнадцатеричных знаков (64 случайных бита),
  частота проверок — не больше 40 за 10 минут с адреса, затем 429 (`test/requests-lifecycle.test.js`).
  Ссылка проверки в PDF и на странице справки — `/#/verify/<код>`: кода демо-кабинета в ней нет, и проверка
  не ставит cookie кабинета. Кабинет справки сервер находит по указателю «код → кабинет»; человек, которому
  показали PDF, видит только «справка действительна» (`test/sandboxes.test.js`, `test/browser-review-1122.py`).
- PDF справки (`/api/requests/:id/document.pdf`) отдаётся только владельцу и только готовой электронной справке:
  тот же `own()`, что у страницы; чужая — 404, неготовая — 409 (`test/document-pdf.test.js`).

## Пароли не хранятся в открытом виде

- `server/security/password.js`: scrypt (N=16384, r=8, p=1), 16 байт случайной соли, 64 байта ключа.
  В базе строка `scrypt$N$r$p$соль$хеш`.
- Сравнение через `timingSafeEqual`; если логина нет, всё равно считается scrypt, чтобы
  уменьшить разницу во времени ответа для существующих и отсутствующих пользователей.
- Перебор: 5 неудачных попыток на пару «адрес + логин» и 30 на адрес за 15 минут, затем 429 с
  `Retry-After`. Смена пароля требует текущий пароль, проверяет сложность и закрывает остальные сеансы.
- Демо-пароль `mgimo2026` публичный и показан на странице входа ради жюри; в базе — только его хеш.
  В демо новый пароль проверяется, но не сохраняется, и профиль это прямо подписывает;
  при `DEMO_MODE=0` смена пароля работает полностью.

## Ключи сервисов не лежат в коде и в браузере

- Все настройки — из окружения (`server/config.js`), `.env` исключён из репозитория, в
  репозитории только `.env.example` с пустыми значениями ключей провайдеров.
- ИИ-помощник вызывает настроенного провайдера **с сервера** (`server/domain/assistant.js`);
  браузер отправляет вопрос и недавние реплики. Контекст учебных данных собирается сервером
  только для владельца текущей сессии. Модель не получает произвольный доступ к базе.
- Без ключа помощник работает на правилах, кабинет полностью функционален.

## Сессии и запросы

- Токен сессии — 32 случайных байта в cookie `HttpOnly; SameSite=Lax; Path=/`, в продакшене
  `Secure` и префикс `__Host-`. В базе хранится SHA-256 от токена: утечка базы не даёт войти.
- Сессия живёт 12 часов и истекает после 2 часов простоя; не больше 10 сеансов на пользователя.
  Выход удаляет сессию на сервере.
- Изменяющие запросы с действующей сессией требуют её CSRF-токен (`X-CSRF-Token`).
  Если заголовок Origin присутствует, сервер проверяет его; тело разбирается как JSON с лимитом 64 КБ.
- Браузер передаёт CSRF также при чтении API. Если общая cookie уже принадлежит другому
  сеансу, сервер возвращает `403 SESSION_CHANGED` до чтения данных или изменения заявки;
  вкладка очищает интерфейс и загружает текущий сеанс заново. Старый запрос не повторяется
  автоматически от имени нового студента.
- Вход и выход сообщаются соседним вкладкам через BroadcastChannel и событие storage.
  Передаётся только сигнал без данных пользователя и токенов; временная запись сразу удаляется.
  Фокус вкладки, возврат из фонового режима и восстановление из кеша браузера дополнительно
  проверяют сеанс. Перезагрузка очищает прежние формы, историю чата и кеши модулей.

## Заголовки и вывод

- CSP: скрипты, стили и шрифты только со своего домена, `frame-ancestors 'none'`, `object-src 'none'`.
  Шрифт Onest раздаётся локально, поэтому при открытии кабинета браузер не обращается к сторонним
  сервисам; тест проверяет, что в политике нет внешних адресов.
- `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: same-origin`,
  `Permissions-Policy`, HSTS в продакшене.
- Все данные в интерфейсе выводятся через экранирование (`esc`), SQL — только с плейсхолдерами.
- Статика отдаётся только из `public/`: путь нормализуется, обход каталогов отсекается.
- Ошибки сервера не раскрывают стек: подробности уходят в журнал, клиенту — общее сообщение.

## Персональные данные

- Хранятся только учебные данные: нет паспорта, СНИЛС, адреса.
- Номер зачётки и телефон в профиле скрыты до нажатия «показать».
- Учебные данные и история помощника не записываются приложением в localStorage. Они находятся
  в памяти вкладки; cookie сессии хранится браузером. При выходе сервер удаляет сессию,
  а интерфейс должен очистить данные предыдущего аккаунта и закрыть его диалоги.
- IP в списке сеансов показывается наполовину.
- Действия деканата и входы пишутся в журнал (`audit_log`).

## Игровой слой

- Баланс М-коинов, открытие вещей и рекорд считает сервер; закрытую вещь нельзя надеть запросом к API.
- Забег: сервер выдаёт токен и отмеряет время, счёт и монеты обрезаются по реальной длительности
  забега, дневной лимит 5 минут хранится в базе, а не в браузере.

## Границы демонстрационного стенда

- Тестовые пароли специально опубликованы для жюри. На стенде (`DEMO_SANDBOXES=1`) у каждого проверяющего
  свой демо-кабинет — отдельная SQLite, которая создаётся только после верного пароля и запоминается в cookie
  `__Host-mm_demo` (HttpOnly, SameSite=Lax, Secure). Неверный пароль не оставляет ни базы, ни cookie кабинета;
  одновременные входы из одного браузера попадают в один кабинет. Код кабинета — 80 случайных бит; кто знает
  ссылку `/?demo=<код>`, входит в тот же кабинет, поэтому её показывает только окно «Ваш демо-кабинет» вошедшему
  владельцу — для своего второго окна. «Начать с чистого кабинета» работает только из открытого сеанса.
  Заявки, объявления, прочитанное и сеансы одного кабинета не видны в другом (`test/sandboxes.test.js`,
  `test/browser-review-fixes.py`, `test/browser-review-1122.py`). Новых кабинетов — не больше 20 в час с адреса
  (место занимается до создания базы, параллельные входы лимит не обходят) и 400 всего ([ADR-012](ai/DECISIONS.md)).
- Без демо-кабинетов (локальный запуск) база общая; тогда список сеансов показывает только текущий,
  а закрыть чужие сеансы под общим логином нельзя (403).
- Объявления и изменения расписания от демо-аккаунта деканата видят все студенты факультета этого кабинета.
  Публикации ограничены: 10 за 10 минут на сотрудника в кабинете, затем 429 с `Retry-After`;
  ошибочные формы лимит не расходуют (`test/dean-limits.test.js`). Текст объявлений выводится
  с экранированием, поэтому разметку или скрипт через него не внедрить; браузерный сценарий
  `test/browser-xss.py` проверяет это на объявлении и комментарии к заявке при 360 и 1366 px.
- `style-src 'unsafe-inline'` в CSP оставлен намеренно: интерфейс собирается из шаблонов со встроенными
  атрибутами `style` (размеры, цвета, позиции), и без этого разрешения они бы не применились. Скрипты
  `unsafe-inline` не получают: `script-src` только `'self'`. Остаточный риск: внедрённая разметка
  могла бы менять оформление страницы, хотя исполнить скрипт ей мешает `script-src 'self'`. Вынос стилей в классы — задача после конкурса.
- Лимит входа считается по паре «адрес + логин» (5 за 15 минут) и по адресу (30). Злоумышленник с одного
  адреса не закроет вход жертве, пришедшей с другого. Но общего счётчика по логину без адреса нет:
  распределённый перебор одного логина с многих адресов этим лимитом не остановить. Для вымышленных
  аккаунтов с публичным паролем это допустимо; для боевой системы нужен дополнительный счётчик.
- Локальный HTTP служит разработке. Публичный стенд должен работать через HTTPS с Secure-cookie.
- `TRUST_PROXY` включается только за управляемым прокси, который заменяет входящий
  `X-Forwarded-For`; иначе клиент сможет влиять на определение IP для лимитов.
- Файл SQLite и резервные копии хранятся вне `public/`, на постоянном диске, с доступом только
  серверного процесса. Потеря временного диска приведёт к потере изменений.
- Условия обработки внешним ИИ-провайдером не заменяются настройками кабинета. В конкурсном
  прототипе используются только вымышленные данные. Ответы помощника не меняют оценки и
  статусы заявок: соответствующие действия проходят отдельную серверную проверку.
